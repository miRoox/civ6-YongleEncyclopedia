## 实测中修复的问题

`GetNumGreatWorkSlots`、`GetGreatWorkInSlot`、`GetGreatWorkTypeFromIndex` 仅存在于 UI 环境。原先把库存扫描放在 Gameplay 的实现不能正常运行。

现在由 `UI/YongleEncyclopedia_UI.lua` 扫描库存，经 `UI.RequestPlayerOperation(..., PlayerOperations.EXECUTE_SCRIPT, ...)` 提交获取通知；Gameplay 脚本负责实际提升、同步随机抽取和持久化防重复属性。ModBuddy 工程增加 ImportFiles、AddUserInterfaces 动作，完整重启游戏后，日志确认两个环境的脚本均已加载。此次创作和考古均实际触发了获取处理器。

数据库 Gameplay 外键验证通过，模组 SQL、文本、图标、美术和脚本组件加载成功。日志中仍存在官方 `CurrentClickouts/.../ClickoutText_en_US.xml` 的重复本地化标签错误，来源不在本模组。

## 测试准备与复现

FireTuner 用于增加伟人点数、推进原版伟人池、补充施工进度、解锁自然历史和移动考古学家。剧院广场通过正常生产界面选址。考古学家通过城市生产队列建立，保留正确的博物馆归属。

为抽到稀有残篇，重载发掘前检查点，消耗两次同步随机数，并以 `ResourceBuilder.SetResourceType` 恢复同一文艺复兴遗址，走原版发掘及文明选择流程重复抽取；本轮第三次获得残篇。没有改动生产数据库或把残篇临时绑定给伟人。此测试证明能进入原版候选流程，不用于测量自然出现概率。

相关 FireTuner 接口细节：

- 发掘操作使用 `GameInfo.UnitOperations.UNITOPERATION_EXCAVATE.Hash`；本机未提供 `UnitOperationTypes.EXCAVATE` 常量。
- 移槽操作需包含 `PlayerOperations.PARAM_PLAYER_ONE`、源／目标城市、源／目标建筑、巨作实例和目标槽。最终验收使用完整参数；准备阶段一次缺少玩家参数的试验已读档重做。
- `GetBuildingYieldFromGreatWorks(yieldIndex, buildingIndex)`；旅游接口为 `GetBuildingTourismFromGreatWorks(false, buildingIndex)`。
- 勿根据同一帧的旧 UI 缓存判断产出未生效；核对 Gameplay 城市产出、刷新后的面板及下一回合实际结算。
- 调试准备中一次误用 `CreateDistrict` 触发了引擎访问异常，后续改用正常区域选址流程；上述验收在恢复后的对局完成。

本地测试存档位于游戏的 `Saves/Single/`：

- `Yongle_Runtime_PreRecruit.Civ6Save`：剧院广场和槽位已准备，解缙尚未招募。
- `Yongle_Runtime_PreDig.Civ6Save`：考古学家位于文艺复兴遗址，尚未发掘。
- `Yongle_Runtime_Fragment.Civ6Save`：已经获得残篇、尚未激活解缙，可查看五项文艺复兴提升。
- `Yongle_Runtime_NoRepeatBoth.Civ6Save`：两件巨作均已取得，刻意撤销膛线提升，用于验证读档不重复奖励。
- `Yongle_Runtime_BothWorks.Civ6Save`：两件巨作均已取得，调试撤销的提升已恢复，供直接查看展示及产出。
